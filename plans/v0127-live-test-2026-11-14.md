# v0.12.7 live test on the HP M283fdw — 2026-11-14

Status: passed for what 0.12.7 changes. It also confirmed a separate defect
that 0.12.7 does not fix (see "Findings"). No code changes were made during
the test.

Setup: Home Assistant 2026.10.4, HP Color LaserJet MFP M283fdw
(`NPIC25FE4.local`, UUID `564e424b-4e37-4a33-3554-b05cdac25fe4`). Test input:
three labeled Letter pages (`ESCL-1207-P1..P3`) printed from the Mac and run
through the feeder each time. Every scan used Feeder, Letter, 300 DPI, color,
one-sided.

## What the scanner advertises

Read with `dns-sd -L` and plain `ScannerStatus` GETs:

- `_uscan._tcp` on port **8080**, `rs=eSCL`, lowercase `uuid` TXT key.
- `_uscans._tcp` on port **443**.
- `ScannerStatus` answers 200 on ports 80, 8080 and 443.

This matches the M277dw from PR #17: the advertised HTTP port is 8080.

## Starting state

The config entry was created manually (`source: user`) but held port 8080 in
both data and options. Rediscovery under 0.12.6 or earlier had overwritten the
user's port: the exact bug PR #17 reports.

## Results

1. **0.12.6, port 8080:** the scan failed with `scanner returned a job URL
   outside its origin`. The HP had already accepted the job and begun feeding
   pages. The integration never tracked the job, so it stayed `Processing`.
   The tester deleted that one job (the one this test created) by its path on
   port 8080 (200), and the scanner returned to Idle.
2. Updated to 0.12.7 through HACS, restarted Home Assistant. Diagnostics showed
   0.12.7, entry loaded, data and options port still 8080.
3. Saved port 80 through the real options flow with every other value
   unchanged. Options gained port 80 plus the form defaults for `base_path`
   and `rotate_duplex_backs`; data stayed on 8080.
4. **0.12.7, port 80:** scan `bceaf2ccb2b6` completed, 3 pages. PDF 1,091,365
   bytes, 3 Letter pages (612 x 792 pt), all pages upright and legible with
   all four border edges present. Authenticated download 200, anonymous 401.
   SHA-256 `d04af301ef0526b01f75ebf5e1c8db6a278ded27a43fcae89c89bde63a99695d`.
5. Restarted Home Assistant. The scanner keeps advertising 8080. After the
   restart the options port was still **80**; under 0.12.6 rediscovery would
   have overwritten it with 8080. Entry loaded and the scanner was reachable.
   The restart was not proven to trigger a Zeroconf flow, because Home
   Assistant does not log discovery that ends in `already_configured`. For a
   `source: user` entry 0.12.7 never changes the port anyway.
6. **0.12.7 after restart:** scan `0cead1f647a0` completed, 3 pages, PDF
   1,088,807 bytes, visually identical to step 4.

The entry is left on port 80 because that is the only HTTP port that scans
on this device.

## Findings that 0.12.7 does not fix

- **Discovery-created entries cannot scan on HP.** Discovery stores the
  advertised port 8080. On 8080 the HP returns its job `Location` with an
  explicit `:80`, so `_absolute()` rejects it. Reproduced on this device in
  step 1. Any new user who adds the scanner through discovery hits it.
- **A rejected job URL leaves the job running on the scanner.** The rejection
  happens after the device has accepted the job, so nothing cancels it and the
  feeder keeps pulling paper.

Fix design is deferred until after this test, as agreed; see
`open-questions.md`.
